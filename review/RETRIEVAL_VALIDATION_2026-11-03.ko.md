# 참고 그림 자동 선택 검증 결과

- 검증일: 2026-11-03, Asia/Seoul 기준임.
- 결론: **6종 요청·총 7회에서 원본 전체 후보 입력이 시험용 Codex CLI 경로의 문자 수 제한으로 거절됨. 선택 품질을 평가할 실모델 표본은 확보하지 못함.**
- 확인된 장애: 원본 검색 요청은 약 299만 자이나, 시험한 `turn/start` 입력 경로는 최대 1,048,576자로 제한됨.
- 판정 범위: 해당 CLI 입력 경로의 전달 제약 확인임. Codex 모델 전체의 문맥 한도나 참고 선택 능력에 대한 판정은 아님.
- 원본·이식 구현·다운로드 데이터는 수정하지 않았으며, 이미지 생성은 수행하지 않았음.

## 1. 시험 설계

- 원본 기준: PaperBanana-Interact `ed08ef7e427ce147194af91d8ae6326a6cbc9cbd`임.
- 데이터: `data/prepared/MTPaperBananaBench/ref.json`의 원래 순서 앞 200개임.
- 시험 입력: 사용자 비공개 논문 대신 합성 방법론·캡션 6종을 사용함.
- 선택 목표: 원본 지시대로 관련 diagram ID 10개 반환임.
- 사전 계획: 6종을 각 2회까지 실행하고 정상 선택 시 관련성·반복 선택·Planner 연결을 비교하는 방식임. 공통 입력 경계가 확인되면 불필요한 추론 반복을 중단하는 조건임.
- 실제 수행: 6종 각 1회와 첫 요청 재시험 1회, 총 7회의 입력 전달 시험임. 동일 backend의 짧은 대조 요청 1회는 별도 수행함.
- 중요 구분: 7회는 **선택 품질 표본 7개가 아니라 입력 거절 재현 7회**임. 의미 판단의 통계적 품질 검증은 수행되지 못함.

## 2. 실행 방법과 원본 대응

- 실제 실행기: 설치된 `codex-cli 0.166.0-alpha.5.1`의 `codex exec`임.
- 인증: 기존 ChatGPT 로그인 사용임. 자식 실행 환경에서 `OPENAI_API_KEY`, `CODEX_API_KEY`를 제거하여 별도 API 키 사용을 방지함.
- 모델 요청: 기존 사용자 설정에서 확인한 `gpt-6.1-sol`, reasoning effort `high`임. 서버의 실제 내부 모델 빌드까지 확인한 것은 아님.
- 실행 옵션: `--ignore-user-config --ephemeral --skip-git-repo-check -s read-only --json`과 stdin 입력 사용임. 사용자 설정 파일 수정이나 전역 스킬 설치는 수행하지 않았음.
- CLI 사용법의 근거: [OpenAI 공식 비대화형 실행 문서](https://learn.chatgpt.com/docs/non-interactive-mode)와 설치된 CLI의 `exec --help` 확인임. 이번 문자 제한 판정의 직접 근거는 문서가 아닌 실제 오류 로그임.
- 현재 PaperSketch는 활성 Codex 채팅이 bridge 요청 파일을 처리하는 방식임. 이번 CLI는 독립된 입력 전달 시험 경계이며, 스킬에 새 backend를 연결하거나 활성 채팅의 전체 실행을 재현한 것은 아님.
- 원본의 system instruction은 host 작업 지시 안에 전문으로 포함함. 원본 Gemini API의 system 슬롯과 동일한 권한·모델 설정으로 실행한 것은 아님.

### 패키지 환경과 요청 구성의 한계

- 기존 uv 요구사항을 오프라인 캐시에서 해석하는 초기 시도가 실패함. 이 단계에서는 모델 호출이 없었으며 새 패키지 다운로드·설치를 수행하지 않았음.
- 이후 표준 라이브러리 harness로 원본 `RetrieverAgent`·`PlannerAgent` class AST와 `BaseAgent.__init__`를 실행함. SDK config 생성은 같은 설정 dictionary를 반환하는 시험용 경계로 대체함.
- 후보 선택 응답을 모의 생성하거나 검색 알고리즘을 바꾼 것은 아님. 모델 응답이 있었다면 strict JSON 계약을 검사하도록 구성했으나 실제 선택 응답은 없었음.
- 이 방식은 원본 요청 구성을 확인하기 위한 경계 시험임. 원본 SDK·provider·전체 runner 통합 실행의 성공을 의미하지 않음.
- 생성된 요청은 기존 원본/이식본 차등 실행 기록과 대조함. 모든 6종의 config와 `Candidate Pool` 이후 전문이 기존 기록과 동일함.
- `retriever_agent.py`, `planner_agent.py`, `base_agent.py`의 현재 원본/보존본 byte 동일성도 별도 확인함.

## 4. 해석과 다음 대응

### 확인된 사실

- 원본의 전체 후보 요청 구성 자체는 재현됨.
- 시험한 CLI 경로에서 원본 크기의 단일 텍스트 요청을 전달할 수 없음.
- 요청 주제를 바꾸거나 같은 입력을 재시도해도 같은 크기 제한이 발생함.
- 원본 user 요청만으로도 한도를 초과하므로 짧은 host 머리말을 제거하는 것으로 해결되지 않음.

### 확인하지 못한 사항

- Codex의 실제 참고 선택 관련성·원문 활용 정도·모델 내부 문맥 한도임.
- 활성 채팅의 도구 읽기나 다른 입력 표현 방식에서 동일 전문을 한 번의 추론 입력으로 전달할 수 있는지 여부임.
- 이미지 10개와 전문을 받는 Planner의 실제 모델 처리·결과 품질임.
- 원본 Gemini/OpenRouter backend의 같은 입력에 대한 처리 성공·품질임. 원본 유료 API 호출은 수행하지 않았음.

### 권장 순서

1. 원본 후보·본문·캡션을 유지한 채 전달 가능한 Codex 입력 경계부터 확인할 필요가 있음. 문자 수 제한과 모델 token 문맥 한도를 구분하여 검증할 필요가 있음.
2. 파일 입력·여러 입력 part 등 다른 전달 방식은 지원 여부와 실제 입력 누락 여부를 별도 확인한 뒤 채택할 필요가 있음. 이번 결과만으로 가능한 해결책이라고 단정하지 않음.
3. 전체 입력 전달이 가능해지면 준비된 6종을 각 2회 실행하여 선택 ID·관련성·반복 일관성·실제 Planner 전달을 평가할 계획임. 이는 최소한의 기능 탐색 표본이며 원본 대비 성능 동등성 평가에 충분한 표본이라는 뜻은 아님.
4. 전체 전달이 불가능하면 요약·후보 축소·분할 검색은 원본 검색 알고리즘 변경으로 명시하고 별도 결정할 필요가 있음. 이번에는 해당 대체를 수행하지 않았음.

## 5. 증거와 변경 범위

- 시험 harness: `runs/retrieval-validation-2026-11-03/validate.py`임.
- 독립 결과 집계: `runs/retrieval-validation-2026-11-03/verify_evidence.py`임.
- 요청별 전문: 해당 폴더의 `requests/*/request.json`, 유형별 `prompt.txt`, `input.json`임.
- 실제 출력·오류: 유형별 `trial-N/{events.jsonl,stderr.log,outcome.json}`과 control 폴더임.
- 종합 결과: `summary.json`, `construction.json`, `evidence-check.json`임.
- 별도 evidence 집계는 6종·7회 거절, 대조 응답, 원본 byte 동일성, 기존 차등 기록과 후보 전문·설정 동일성을 assertion으로 검사하여 통과함.
- 시험 실행 전후 보호 대상 소스·문서·원본/사본 데이터 1,751개 파일의 hash 불변 확인됨. 이 비교 이후 검증항목 문서에 결과를 추가 기록함. 원본 세 저장소의 커밋과 작업 트리 무변경도 재확인됨.
- 변경 범위: 검증 전용 runs 파일, 본 보고서, 검증항목 문서의 상태 기록뿐임. 구현 수정·이미지 생성·커밋·푸시는 수행하지 않았음.
